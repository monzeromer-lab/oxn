# Load results — oxn 0.3.0 (Phase 2 campaign)

Recorded 2026-10-14 with `oxn-load` against the dedicated local Redis 8.0.5
(`scripts/test-redis.sh`, :6390, reset before every run; AOF only for
`redis-restart`), release build, one machine. Same setup and the same
commands as [the 0.2.2 baseline](baseline-0.2.2.md); run it all with
`scripts/load-campaign.sh`.

**All 17 scenarios pass.** Every run checks every job against a per-job
ledger (no lost, duplicated or wrongly-classified job), the queue
invariants, oxn's own metrics against the ledger and the raw event stream,
and that cleanup leaves no key behind.

## The baseline's scenarios, before and after

| Scenario | 0.2.2 | 0.3.0 | jobs | ok/s 0.2.2 → 0.3 | pickup p99 0.2.2 → 0.3 |
|---|---|---|---|---|---|
| `smoke --retention last1000` | ❌ 3,877 leaked hashes (B5) | ✅ | 5,000 | 1,756 → 1,858 | 947ms¹ → 940ms¹ |
| `smoke --retention remove` | ✅ | ✅ | 5,000 | 1,807 → 1,870 | 1,000ms¹ → 963ms¹ |
| `mixed` | ❌ 6,250 orphaned hashes (B5) | ✅ | 10,000 | 2,706 → 2,575 | 1,424ms¹ → 1,615ms¹ |
| `latency` (default `drain_delay`) | ❌ workers slept 5s (B3) | ✅ | 7,992 | 196 → 200 | **5,001ms → 2.1ms** |
| `shutdown` (restart under load) | ❌ in-flight jobs failed (B4) | ✅ | 10,000 | 538 → 538 | 6,795ms¹ → 7,066ms¹ |
| `smoke` + `script-flush` + `client-kill` | ❌ result lost (B15) | ✅ | 20,000 | 1,619 → 1,619 | 366ms → 40ms |
| `kill-worker` (SIGKILL ×4) | ✅ | ✅ | 20,000 | 926 → 928 | 12,534ms¹ → 12,526ms¹ |
| `network` (200ms latency, drops, blackhole) | ✅ | ✅ | 20,000 | 680 → 680 | 102ms → 45–164ms² |
| `retry-storm` (30% transient, 4 attempts) | ✅ | ✅ | 20,000 | 3,151 → 3,180 | 17.9ms → 2.5ms |
| `redis-restart` (AOF, restart at 8s) | ✅ | ✅ | 20,000 | 895 → 883 | 300ms → 140ms |

² Three runs: 154, 45 and 164ms. The p99 depends on where the injected

## Phase 2 scenarios

| Scenario | Shape | Result |
|---|---|---|
| Throughput | 1,000,000 jobs, 4 producers, 8 workers × 16 | ✅ 5,861 ok/s, pickup p99 2.3ms, no job lost or duplicated |
| Throughput, multi-process | 300,000 jobs, 8 worker processes | ✅ 5,439 ok/s, pickup p99 2.5ms |
| Throughput, bulk adds | 200,000 jobs, adds in bulks of 100 | ✅ 9,680 ok/s (worker capacity) |
| Graceful shutdown | 20,000 jobs of ~200ms, workers restarted twice, 10s `shutdown_timeout` | ✅ 0 jobs failed by shutdown, 0 released (all in-flight jobs finished) |
| Flow fan-out | 10,000 parents × 10 children, all failure modes | ✅ every parent ran once, after its children; release p99 5ms |
| Flow under chaos | 3,000 × 8, worker restarts every 3s, client kills every 4s | ✅ release p99 13–32ms |
| Schedulers | 50 schedulers × 10 instances, every 200ms, restarts + client kills | ✅ 5,100 ticks, 0 duplicate, 0 missing, lateness p99 13ms |
| Soak | 15 min at 1,500 jobs/s, bounded mixed retention | ✅ 1.35M jobs; keys 1,913 → 1,894 (−1.0%), memory 15.6 → 15.6MB (−0.3%) |

The soak's leak check compares an early window (after a 3-minute warm-up)
with the last 15% of the run; growth over 5% fails. It was shortened from
2h because leaks are per job, not per hour: 1.35M jobs vs 2.16M in the 2h
preset, after the same warm-up. What it can't catch is slow time-driven
growth (allocator fragmentation over hours); run the full length
unattended with `SOAK=2h scripts/load-campaign.sh` (or
`oxn-load run --scenario soak`). A control run with `--retention keep`
(which grows by design) fails it: keys +37%, memory +35%.

## Throughput vs 0.2.2

Same-day, same machine, 200k jobs, 4 producers adding one job per round
trip:

| | ok/s | pickup p50 | pickup p99 | Redis time / job |
|---|---|---|---|---|
| 0.2.2 | 8,639–8,849 | 10–11ms | 47–70ms | 82µs |
| 0.3.0 as of B15 | 5,822–5,885 | 1.4ms | 2.3ms | 132µs |
| 0.3.0 (this campaign) | 6,539–6,569 | 1.3ms | 2.2ms | 112µs |

Both are bound by Redis CPU (~90% of one core). Profiling (`INFO
commandstats`, the slowlog and per-script variants) found:

- **Every script re-ran the whole shared prelude.** Redis executes a
  script's top level on each `EVALSHA`, so all ~22 helpers in
  `common.lua` were allocated as closures on every call (~3.5µs). A
  `build.rs` now gives each script only the helpers it references:
  `move_to_active` carries 3, `add_job` 5.
- **`move_to_finished` wrote fields to a hash it was about to delete**
  (`remove` retention) and decoded the job's options JSON on every
  deletion to look for a dedup pointer; the requeue paths decoded it for
  the priority alone. Both now skip the work.
- **The rest is what 0.3 does on purpose:** deleting every key a job owns
  (B5), waking idle workers at once (B3), flow and idempotency
  bookkeeping. With no backlog, a woken worker sometimes loses the race
  for the job to one that just finished: 0.55 empty fetches per job.
  0.2.2 never had idle workers — its pickup was 10ms at p50 — so it spent
  that Redis time on jobs.

With adds batched (`--bulk 100`) the same workers complete 9,680 jobs/s,
above 0.2.2's 8,700, so worker capacity is not what dropped. Hot-path
script cost per job (micro-benchmark, add → take → complete): 0.2.2
62µs, 0.3.0 as of B15 87µs, now 71µs. Further levers, not done: fetching
several jobs per call when a worker has free slots, and Redis Functions
(Redis 7+), which load helpers once instead of per call.

## Harness bugs found during the campaign

Not oxn bugs, but each one would have made a run report the wrong thing:

- **The invariant check was quadratic.** It looked each job up by scanning
  every container; on 110k-job snapshots one check took ~100s, blocking
  the run's own monitoring. It now builds an index once (flow-10k: 179s →
  21s wall time).
- **Checks are paced to ≤10% of the time.** A snapshot of a big queue
  blocks Redis while it is taken; checking every 3s regardless slowed the
  load being measured by a third.
- **The flow harness retried only the first 1,000 failed children.** When
  permanent failures crossed 1,000, later `retry`-flow children were never
  retried and their parents waited forever.
- **A `reset` without `OXN_REDIS_PERSIST=1` before `redis-restart`** starts
  Redis without AOF, so the restart wipes the data. The campaign script
  does it right.

## Reports

Every run's report (per-second timeline, per-job anomaly histories, Redis
state after drain, plateau, oxn metrics) is written to
`<cargo target dir>/oxn-reports/load/`.

## Reproduce

```bash
scripts/load-campaign.sh                  # all 17 scenarios, ~45 min
SOAK=2h scripts/load-campaign.sh          # with the full-length soak
ONLY=throughput scripts/load-campaign.sh  # one scenario
```
